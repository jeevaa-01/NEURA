# Search & Discovery Architecture

Phase 16 provides one protected search surface for messages, thread replies,
channels, people, files, knowledge, tasks, and accessible workspaces.

## PostgreSQL-first strategy

PostgreSQL is intentionally used as the initial search engine to keep NEURA
lightweight. The search service uses bounded Prisma `contains` queries with
case-insensitive matching, then applies a small deterministic ranking layer in
the application. It does not add Elasticsearch, OpenSearch, or another search
server. The service boundary can later be replaced with PostgreSQL full-text
search, pg_trgm, or a dedicated provider without changing the API contract.

`GET /api/search` accepts a validated query, type, workspace, channel, user,
date range, cursor, and limit. Results are merged, deduplicated, ranked, and
returned using a stable `SearchResult` shape. Candidate queries are bounded and
the response defaults to 20 results with a maximum of 50. Pagination uses an
opaque offset cursor over the bounded merged result set.

## Authorization model

The service resolves the signed-in user's active workspace memberships first.
It then derives accessible channels through the existing
`listAccessibleChannels` and `canAccessChannel` services. Database candidate
queries are constrained to those workspace and channel IDs before any result
is serialized. React never receives unauthorized candidates to filter.

Private and archived channel visibility therefore follows the existing owner,
admin, membership, and lifecycle rules. Files exclude deleted attachments and
deleted messages. Knowledge results require ready sources/documents and exclude
deleted file-backed sources. Tasks are scoped to accessible workspaces. People
results expose only public profile fields; email is searchable as an input to
the server query but is never returned.

## Resource integrations

- Messages and replies use the existing `Message` thread relationship and link
  to the channel. Reply results link to their root message and open its thread
  when the channel is entered.
- Channels use accessible names and descriptions only.
- People use active workspace membership and existing profile conventions.
- Files use Phase 15 attachment metadata and authorized `/api/files/:id`
  downloads. Storage keys and filesystem paths never enter the result contract.
- Knowledge searches use ready `KnowledgeSource`/`KnowledgeDocument` rows for
  fast keyword results. When a single workspace is explicitly selected and an
  embedding key is configured, the existing Phase 11 `retrieveKnowledge`
  service contributes semantic candidates. Normal search never invokes an LLM.
- Tasks use the existing `WorkspaceTask` foundation and workspace membership;
  no new task system is introduced.

## Ranking and snippets

Exact phrase matches, exact field matches, token matches, prefix matches, and
recency produce a deterministic relevance value. The value is used internally
for ordering and is not displayed as a score. Snippets are plain text with
control characters normalized. The client highlights query terms with React
elements, never injected HTML.

## UI and navigation

The existing shell search trigger opens the search destination, and the search
page now provides a debounced input, type/workspace/channel/date filters,
loading/error/empty states, recent searches in bounded browser storage, and
load-more pagination. Result links are generated by the server from known
route templates. Direct file links still pass through the Phase 15 access
check, and message channel links re-check channel access when opened.

## Performance and future path

Queries use `select`, bounded `take` values, existing relationship indexes, and
parallel resource queries. No search cache is added because authorization and
freshness are more important at this scale. If the dataset outgrows these
bounded PostgreSQL queries, the same authorization pre-filter and typed result
contract can front PostgreSQL full-text/trigram indexes or a dedicated search
infrastructure later.
