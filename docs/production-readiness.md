# NEURA — Production Readiness

Phase 17 hardening notes for deploying the existing platform without adding a
second database, search cluster, or realtime vendor.

## Architecture and integration

NEURA keeps workspace membership as the tenant boundary:

```text
workspace → channels → messages/threads/files
                         ├→ knowledge/RAG → AI
                         ├→ tasks/actions → agents/workflows
                         └→ notifications/activity → SSE realtime
                                           └→ unified search
```

Protected pages use the platform layout and `requireSession`. Protected API
routes resolve the session first and then use the existing workspace/channel
authorization services. PostgreSQL is authoritative for saved state; Redis is
used for rate limiting and realtime fan-out, so a realtime failure does not
prevent messages, notifications, or search from being persisted or queried.

## Security model

- Workspace, private-channel, message, file, knowledge, task, workflow, AI,
  notification, activity, search, and realtime reads/mutations are scoped by
  the authenticated user and server-side relationships.
- Browser-provided IDs are treated as selectors only; ownership, membership,
  role, and channel visibility are rechecked on the server.
- AI tools use existing authorization and action-confirmation services. They do
  not receive arbitrary SQL, shell, or filesystem capabilities. Provider keys
  remain server-only.
- Uploaded files use server-side size, MIME, extension, signature, and text
  validation. Local storage is resolved outside `public`, keys are generated by
  NEURA, and downloads recheck channel access. Deleted messages/attachments do
  not serve file bytes.
- Baseline headers are applied by Next.js: `nosniff`, frame denial, a strict
  referrer policy, a restrictive permissions policy, and HSTS in production.
  A strict CSP is present for production; its script/style allowances reflect
  the current Next/Better Auth runtime.

## Rate limits and reliability

- Better Auth retains its in-process credential limits as defense in depth. A
  Redis-backed outer limiter protects sign-in (20/minute per trusted client
  address), sign-up (10/5 minutes), password reset/change and verification
  operations (10/5 minutes), and account updates.
- Redis-backed limits also cover profile/avatar/account mutations, authenticated
  search (60/minute), file uploads (20/minute), AI (20/minute per user and
  workspace), and realtime connection openings (30/minute). Rate-limited
  responses include `Retry-After`.
- Authentication, AI, account security, and realtime fail closed on Redis
  failure. Search, file processing, and other lower-risk operations degrade
  open with one bounded operational warning; their primary authorization still
  remains server-side.
- Redis is optional for core persistence. Realtime uses authenticated SSE with
  channel authorization and cleanup; clients must recover from reconnects by
  reloading authoritative state.
- API responses expose safe user messages. Provider, Prisma, filesystem, and
  storage details are logged server-side only where needed and are not returned
  to browsers.

## Performance considerations

- Search uses bounded candidate queries, selected Prisma fields, accessible
  channel scopes, deterministic ranking, and cursor pagination. Semantic RAG is
  only attempted for an explicitly selected single workspace.
- Message, file, knowledge, and realtime paths use narrow selects and bounded
  limits. Expensive AI output and workflow execution remain capped by existing
  configuration and service guards.
- The client uses the existing shell, debounced search, lightweight loading and
  empty states, and no polling-heavy feature was introduced.

## Environment and deployment

Required server configuration is documented in `.env.example` and validated by
`lib/validations/env.ts`:

- `DATABASE_URL` — PostgreSQL connection string.
- `REDIS_URL` — Redis connection string for realtime and shared limits.
- `BETTER_AUTH_SECRET` — unique secret of at least 32 characters.
- `NEXT_PUBLIC_APP_URL` and optional `BETTER_AUTH_URL` — deployment origin.
- `OPENAI_API_KEY`, `OPENAI_MODEL`, and AI/RAG limits — optional AI/RAG provider
  configuration; the core collaboration product remains usable without a key.
- `FILE_STORAGE_ROOT` and file limits — private local file storage settings.
- `POSTGRES_*` and `REDIS_PORT` — local Docker Compose settings.

Before launch:

1. Run `npm ci` with the lockfile, then `npm run db:deploy` against the target
   PostgreSQL database.
2. Provide persistent private file storage. The local provider is suitable for
   one instance or a mounted persistent volume; a shared object provider should
   be added before horizontally scaling file-serving instances.
3. Provide Redis for realtime fan-out, AI limits, and search/upload limits.
4. Terminate TLS at the deployment edge, set production origins and secrets,
   then run `npm run build` and a protected-route smoke check.
5. Keep `storage/`, `.env`, and generated secrets out of version control.

Node.js `>=20.9.0`, PostgreSQL, and Redis are the supported runtime baseline.

## Known limitations and scaling path

- Vitest covers launch-critical domain logic. Playwright provides an opt-in
  authenticated browser smoke suite; it requires an isolated deployment with
  PostgreSQL and Redis.
- Better Auth's internal credential counter remains per-process, but the Redis
  outer limiter prevents the documented auth budgets from multiplying across
  application instances. Correct client-address attribution depends on a
  trusted reverse proxy setting `X-Forwarded-For` or `X-Real-IP`.
- Local indexing is synchronous after upload. Failed indexing preserves the
  file and exposes a retryable failed status, but a background queue is the
  natural next step for larger documents or high upload volume.
- There is no antivirus scanner, OCR pipeline, or dedicated full-text/vector
  service. PostgreSQL plus bounded queries is the deliberate lightweight path;
  a shared object store, worker queue, and specialized search index are future
  scaling options only when measured traffic justifies them.
- `npm audit --omit=dev` currently reports four high advisories in transitive
  Prisma tooling (`deepmerge-ts` and `mysql2`). The suggested forced fix would
  downgrade Prisma to a breaking major, so no automatic upgrade was applied;
  review this during dependency maintenance with a compatible Prisma release.
- Authenticated cross-tenant and realtime browser checks remain a deployment
  gate and must run with isolated test data before broad launch.
